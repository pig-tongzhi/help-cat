# 部署、回滚与运维

## 当前运行方式

- Nginx 提供 H5 和管理后台静态文件。
- Nginx 把 `/help-cat-api/` 转发到 `127.0.0.1:18000`。
- `help-cat.service` 启动 Uvicorn，工作目录为 `/opt/help-cat`。
- 后端代码位于 `/opt/help-cat/release/`。
- 数据库位于 `/opt/help-cat/data/help-cat.db`。
- 图片位于 `/opt/help-cat/data/uploads/`。

## 发布原则

1. 代码必须在隔离分支中修改。
2. 先运行自动化测试和语法检查。
3. 发布前创建带时间戳的完整备份。
4. 上传到新的 release 目录，不直接覆盖生产。
5. 比较本地、release 和生产文件 SHA-256。
6. 只有哈希一致才激活发布。
7. 后端变更才重启 `help-cat.service`；纯静态变更不需要重启 API。
8. Nginx 配置变更先执行 `nginx -t`，通过后才 reload。
9. 任一关键验收失败立即回滚。

## 静态资源发布

需要发布的 H5 文件：

```text
app/rescue/index.html
app/rescue/styles.css
app/rescue/api.js
app/rescue/app.js
```

生产目标：

```text
/data/purchase-system/frontend/dist/help-cat/rescue/
```

流程：

1. 将整个当前 rescue 目录复制到 `/opt/help-cat/backups/<timestamp>/rescue/`。
2. 将新文件上传到 `/opt/help-cat/releases/<timestamp>/rescue/`。
3. 在本地和服务器 release 目录按相同文件顺序计算 SHA-256。
4. 哈希完全一致后，用明确文件名安装到生产目录，保持 `nginx:nginx` 所有者和 `0644` 权限。
5. 再次计算生产目录哈希并与本地比较。

不要用未解析的通配符或宽泛目录执行删除/覆盖。

## 后端发布

后端变更需要额外步骤：

1. 备份数据库、当前 `server/helpcat` 包、systemd unit 和 Nginx 配置。
2. 如果有迁移，先在数据库副本上演练。
3. 上传完整且一致的后端包。
4. 执行迁移并记录输出。
5. 重启 `help-cat.service`。
6. 检查服务状态、日志、健康接口和关键 API。

生产数据库不能通过 Git 部署，不能用测试数据库覆盖。

## 回滚

### 静态回滚

把对应时间戳备份中的 rescue 文件恢复到生产静态目录，校验 SHA-256，然后重新访问 H5。

### 后端回滚

1. 停止写入或进入维护窗口。
2. 恢复匹配版本的后端代码。
3. 只有在迁移不可向后兼容时才恢复数据库备份。
4. 重启服务并重复完整健康检查。

数据库回滚必须考虑发布后新增的真实用户数据，不能机械覆盖。

## 发布后检查

- `systemctl is-active help-cat.service`
- `nginx -t`
- `/api/v1/health` 返回 `status: ok`
- H5、后台入口返回 HTTP 200
- H5 静态版本与预期一致
- 管理员角色恢复成功
- 图片读取和上传链路可用
- 生产目录哈希与 release 一致
- 错误日志没有新增持续异常

## 缓存策略

- `index.html` 应设置 `Cache-Control: no-cache, no-store, must-revalidate`。
- CSS/JS 使用版本查询参数，页面发现服务器版本不同后提示用户刷新。
- 不强制刷新正在填写表单的用户。
- 如果未来引入带内容哈希的构建产物，CSS/JS 可使用长期 immutable 缓存。

## 备份与恢复现状

当前已有时间戳备份目录，但仍需补齐：

- 自动数据库备份任务和保留周期。
- 异地或对象存储备份。
- 备份加密与访问审计。
- 定期恢复演练和恢复时间记录。
- PostgreSQL 迁移后的 PITR（时间点恢复）。

## 监控现状

当前只有 systemd/Nginx 日志和健康接口，不足以支撑大规模服务。正式推广前至少增加：

- 请求量、延迟、错误率和资源使用指标。
- 登录、上传、审核和任务领取业务指标。
- 5xx、磁盘容量、数据库锁、备份失败告警。
- 日志集中收集、敏感信息脱敏和关联请求 ID。
