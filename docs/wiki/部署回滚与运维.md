# 部署、回滚与运维

## 当前运行方式

- Nginx 提供 H5 和管理后台静态文件。
- Nginx 把 `/help-cat-api/` 转发到 `127.0.0.1:18000`。
- `help-cat.service` 启动 Uvicorn，工作目录为 `/opt/help-cat`。
- 后端代码位于 `/opt/help-cat/release/`。
- 数据库位于 `/opt/help-cat/data/help-cat.db`。
- 图片位于 `/opt/help-cat/data/uploads/`。

## 发布原则

1. 代码必须在隔离分支中修改。
2. 先运行自动化测试和语法检查。
3. 发布前创建带时间戳的完整备份。
4. 上传到新的 release 目录，不直接覆盖生产。
5. 比较本地、release 和生产文件 SHA-256。
6. 只有哈希一致才激活发布。
7. 后端变更才重启 `help-cat.service`；纯静态变更不需要重启 API。
8. Nginx 配置变更先执行 `nginx -t`，通过后才 reload。
9. 任一关键验收失败立即回滚。

## 打包一个可发布的版本

```bash
scripts/build_release.sh            # 输出到 work/releases/helpcat-<版本>-<时间戳>/
```

脚本只做两件事：把该发布的文件挑出来、生成 SHA-256 清单（第 5 条原则要用的那个）。备份、切换 symlink、`nginx -t`、重启服务仍然在服务器上按下面的流程执行。

产物结构：

| 目录 | 内容 |
|---|---|
| `rescue/` | 居民端 H5 |
| `welcome/` | 欢迎页。**它是站点文档根**（`/` 直接指向它），目录名不能改，否则页内相对路径 404 |
| `admin/` | 管理后台 |
| `backend/` | `server/` 包、`alembic.ini`、依赖清单 |
| `RELEASE` | 版本号、构建时间、精确 git commit |
| `SHA256SUMS` | 全部文件校验和，服务器上用 `shasum -a 256 -c SHA256SUMS` 校验 |

打包器**只从 git 跟踪的文件里挑**，所以产物完全确定：不会带上本地未跟踪文件（例如只存在于开发机上的 `server/__init__.py` 空包标记），也不会夹带调试时留下的临时文件，换一台机器打包结果一致。包里不会出现 `__pycache__`、`*.pyc`、`*.db`、`.env`；`work/` 本身已被 gitignore，产物不会被误提交。

### ⚠️ 线上有两套静态入口，发布必须同时更新

2026-09-23 实测（当时踩过一次：只更新了 `current`，从 IP 访问仍是旧版本）：

| 入口 | nginx server 块 | 静态来源 | API |
|---|---|---|---|
| `helpcat.xyz` / `www.helpcat.xyz` | `server_name helpcat.xyz www.helpcat.xyz` | `/opt/help-cat/current/app/rescue`（跟随 symlink） | `/help-cat-api/` → `127.0.0.1:18000/` |
| `175.178.41.19` | `server_name 175.178.41.19` | **`/data/purchase-system/frontend/dist/help-cat/`**（独立副本，不跟随 symlink） | `/help-cat-api/` → `127.0.0.1:18000/` |

所以一次完整发布 = 切换 `/opt/help-cat/current` **并且** 同步 `/data/purchase-system/frontend/dist/help-cat/{rescue,admin,welcome}`。只做前者，域名入口生效、IP 入口还是旧版本。

```bash
REL=/opt/help-cat/releases/<timestamp>
DIST=/data/purchase-system/frontend/dist/help-cat
mkdir -p /opt/help-cat/backups/<timestamp>-pre-<tag>/dist-help-cat && cp -a "$DIST/." "$_/"
for pair in "app/rescue:rescue" "admin:admin" "app/welcome:welcome"; do
  src="$REL/${pair%%:*}"; dst="$DIST/${pair##*:}"
  cp -a "$src" "$dst.new" && rm -rf "$dst" && mv "$dst.new" "$dst"
done
chown -R root:root "$DIST"; find "$DIST" -type d -exec chmod 775 {} +; find "$DIST" -type f -exec chmod 664 {} +
```

验证要**两个入口分别验**，只看一个会漏：

```bash
for h in 175.178.41.19 helpcat.xyz; do
  curl -s -H "Host: $h" http://127.0.0.1/help-cat/rescue/version.js | grep CURRENT_VERSION
done
```

另外两点实测记录：
- 欢迎页在**域名入口没有 location**（该块 root 直接指向 `app/rescue`），所以扫码进域名根会落在 H5 而不是欢迎页；
  目前欢迎页可通过 `/help-cat/welcome/` 访问（已随本次发布复制过去）。要让域名根就是欢迎页，需要改 nginx 的 root，属于配置变更，需另行确认。
- 线上另有 8000（purchase-system）与 8090（ninebot-ocr）两个 uvicorn，与 help-cat 无关；
  help-cat 只有 `help-cat.service` 一个后端，监听 `127.0.0.1:18000`。

### 改了静态资源就必须升版本号

`app/rescue/index.html` 里的 CSS/JS 全部带 `?v=<版本>` 引用，而这些文件在线上是长缓存。只改 `styles.css` 而不升版本号，对已经访问过的用户**等于没发** —— 实测踩过两次：手机端连续两轮看不到样式改动，就是因为版本号没变、资源 URL 没变。

手工漏升过，所以现在改成脚本：

```bash
scripts/bump_version.sh --check        # 校验两条版本线是否自洽（CI 里也会跑）
scripts/bump_version.sh --next --dry-run   # 看会改哪些文件、各改几处
scripts/bump_version.sh --next         # 真正执行
```

它管两条版本线，落点都写死在脚本里：主版本（`app/rescue/version.js` 的 `CURRENT_VERSION`、
`app/rescue/index.html`、`app/rescue/manifest.webmanifest`、`admin/index.html`、
以及两个钉住字符串的契约测试）和欢迎页版本（`app/welcome/index.html` 的
`data-app-version` 与全部 `?v=`）。

`index.html` 是 `no-cache`，用户普通刷新即可拿到新 HTML，进而引用新的 `?v=` 资源；已打开着的页面由 `checkForUpdate` 发现服务端版本变化并弹刷新提示。

### 运维资产都在 `deploy/` 里

线上配置以前只存在于服务器上，重建或迁移时只能靠回忆。现在纳入版本控制：

| 文件 | 服务器上的位置 |
|---|---|
| `deploy/nginx/helpcat.conf` | `/etc/nginx/conf.d/helpcat.conf`（域名入口 + 站点根是欢迎页） |
| `deploy/systemd/help-cat.service` | `/etc/systemd/system/help-cat.service` |
| `deploy/systemd/help-cat-healthcheck.{service,timer}` | 同上（5 分钟探活） |
| `deploy/systemd/help-cat-backup.{service,timer}` | 同上（每天 03:20 备份） |
| `deploy/logrotate/help-cat` | `/etc/logrotate.d/help-cat` |
| `deploy/journald/help-cat.conf` | `/etc/systemd/journald.conf.d/help-cat.conf` |

改完配置：`nginx -t && systemctl reload nginx`、`systemctl daemon-reload`，再按 `scripts/health_check.sh` 验一遍。

## 静态资源发布

发布整个 `app/rescue/` 目录，不再按文件白名单挑选。完整 release 至少包含：

```text
rescue/                    # app/rescue/ 的完整副本
  index.html
  styles.css
  api.js
  community-form.js
  version.js
  story-77.js
  app.js
  manifest.webmanifest
  assets/brand/
  assets/77/
admin/                     # admin/ 的完整副本
server/                    # server/ 的完整副本
scripts/help_cat_77_seed.py
requirements-commercial.txt
alembic.ini
```

管理后台发布整个 `admin/` 目录，至少包含 `index.html`、`styles.css`、`session.js`、`community-review.js` 和 `app.js`。

生产目标：

```text
/data/purchase-system/frontend/dist/help-cat/rescue/
```

流程：

1. 将整个当前 rescue 目录复制到 `/opt/help-cat/backups/<timestamp>/rescue/`。
2. 建立不可变目录 `/opt/help-cat/releases/<timestamp>/`，把 `app/rescue/` 完整复制到其中的 `rescue/`；不得漏掉 `story-77.js`、`manifest.webmanifest`、`assets/brand/` 或 `assets/77/`。
3. 本地从 `app/rescue/` 递归生成稳定排序的 `rescue.SHA256`，上传至同一 release 根目录；在服务器执行 `cd /opt/help-cat/releases/<timestamp>/rescue && sha256sum -c ../rescue.SHA256`。
4. 切换前以只读临时静态服务暴露该 `rescue/`。逐项读取 `rescue.SHA256`，请求每个文件并要求 HTTP 200，下载响应的 SHA-256 必须等于清单；同时确认每个 HTML 引用资源和 `manifest.webmanifest` 中的图标都在清单内且通过同样检查。
5. 完整校验通过后，原子切换 Nginx root/symlink 到 `/opt/help-cat/releases/<timestamp>/rescue/`，执行 `nginx -t` 后 reload。不要把选定文件覆盖进唯一生产副本。
6. 切换后从正式域名再次验证 `index.html`、`story-77.js`、`manifest.webmanifest`、`assets/brand/`、`assets/77/` 的 HTTP 200 与哈希，再验证 `#story-77`。

清单示例（GNU/Linux 与 macOS 分别使用 `sha256sum` / `shasum -a 256`，输出格式需保持为 `<hash>  <relative-path>`）：

```bash
cd app/rescue
find . -type f -print0 | LC_ALL=C sort -z | xargs -0 shasum -a 256 > ../../rescue.SHA256
```

不要用未解析的通配符或宽泛目录执行删除/覆盖。

## 后端发布

后端变更需要额外步骤：

1. 备份数据库、当前 `server/helpcat` 包、systemd unit 和 Nginx 配置。
2. 如果有迁移，先在数据库副本上演练；升级到 `005_public_profiles` 后必须核对总数、核心 ID 哈希、`normalized_name`、版本字段、QA 标记、`profile_key`、合并自外键、唯一索引、外键检查和猫咪 `community_id` 非空。若出现多条旧 77 marker，迁移应失败并先人工消歧。
3. 把完整 `server/`、`scripts/`、`requirements-commercial.txt` 和 `alembic.ini` 上传到同一个 `/opt/help-cat/releases/<timestamp>/`，计算并核对 SHA-256。
4. 通过 `HELPCAT_DATABASE_URL=sqlite:////opt/help-cat/data/help-cat.db` 执行 Alembic 迁移并记录输出；迁移环境已经显式读取该变量，禁止依赖当前工作目录的默认相对路径。
5. 重启 `help-cat.service`。
6. 检查服务状态、日志、健康接口和关键 API。

生产数据库不能通过 Git 部署，不能用测试数据库覆盖。

## 回滚

### 静态回滚

把对应时间戳备份中的 rescue 文件恢复到生产静态目录，校验 SHA-256，然后重新访问 H5。

### 后端回滚

1. 停止写入或进入维护窗口。
2. 恢复匹配版本的后端代码。
3. 只有在迁移不可向后兼容时才恢复数据库备份。
4. 重启服务并重复完整健康检查。

数据库回滚必须考虑发布后新增的真实用户数据，不能机械覆盖。

## 缓存策略

- `index.html` 应设置 `Cache-Control: no-cache, no-store, must-revalidate`。
- CSS/JS 使用版本查询参数，页面发现服务器版本不同后提示用户刷新。
- 不强制刷新正在填写表单的用户。
- 如果未来引入带内容哈希的构建产物，CSS/JS 可使用长期 immutable 缓存。

## 备份与恢复

`scripts/backup_offsite.sh` 是唯一的备份入口。它不做 `cp` —— 直接在 WAL 模式下复制
数据库会拿到坏副本，所以它用 sqlite3 的在线备份 API 做一致性快照。

```bash
# 备份（服务器上由 help-cat-backup.timer 每天 03:20 自动跑）
scripts/backup_offsite.sh
# 只打印计划
scripts/backup_offsite.sh --dry-run
# 自证「这份备份能恢复」：integrity_check + 行数 + 校验和 + 压缩包可解
scripts/backup_offsite.sh --verify latest
```

一次备份产出 `/opt/help-cat/backups/<时间戳>/`：`help-cat.db`（快照）、
`uploads.tar.gz`、`META.txt`（release、H5 版本、主机）、`SHA256SUMS`。
超过 `HELPCAT_BACKUP_KEEP_DAYS`（默认 14 天）的目录会被清理。

**异地还是必须配置的**。没有配置时脚本会明确告警「这次只落到了本机」，因为同盘
备份在磁盘故障时救不了数据。在服务器 `/etc/help-cat/backup.env` 里挑一种：

| 变量 | 需要装的东西 | 例子 |
|---|---|---|
| `HELPCAT_BACKUP_RCLONE_REMOTE` | `rclone` | `cos:help-cat-backup`（配好 rclone remote，支持腾讯云 COS / 阿里云 OSS / S3） |
| `HELPCAT_BACKUP_COSCMD_BUCKET` | 腾讯云 `coscmd` | `help-cat-1300000000` |
| `HELPCAT_BACKUP_S3_URL` | `aws` CLI | `s3://help-cat-backup` |
| `HELPCAT_BACKUP_UPLOAD_CMD` | 自己的命令 | 以备份目录为唯一参数调用 |

改完 `systemctl restart help-cat-backup.timer`（或 `systemctl start help-cat-backup.service` 立即跑一次），确认日志里出现「已上传到异地」。

恢复步骤（`--verify` 不能代替真恢复演练）：

1. 停写入：`systemctl stop help-cat.service`。
2. 备份现状：`cp -a /opt/help-cat/data/help-cat.db /opt/help-cat/data/help-cat.db.before-restore`。
3. 解包：把快照放回 `/opt/help-cat/data/help-cat.db`，`uploads.tar.gz` 解到 `/opt/help-cat/data/`。
4. `chown root:root`、`chmod 644` 数据库文件；删掉遗留的 `-wal`/`-shm`。
5. 起服务，跑 `scripts/health_check.sh`。
6. 记下恢复耗时（这是 RTO 的唯一真实来源）。

## 监控与告警

三层，缺哪层都会「网站挂了但没人知道」：

1. **探针**：`GET /api/v1/health`（进程活着）与 `GET /api/v1/health/ready`（能查库）。readiness 会真跑一次 `SELECT 1`，数据库锁死/文件丢失/盘满时回 503 —— 只探进程的 liveness 看不到这些。
2. **本地定时探活**：`deploy/systemd/help-cat-healthcheck.{service,timer}` 每 5 分钟调 `scripts/health_check.sh`，检查 readiness、两套静态入口、`systemctl is-active help-cat.service`、`nginx -t` 和数据库盘剩余空间；失败时单元变成 failed（`systemctl --failed` 一眼可见），并 POST 到 `HELPCAT_ALERT_WEBHOOK`。
3. **外部 uptime 监控**（还没做，需要账号）：把腾讯云拨测 / UptimeRobot 之类的 HTTP 监控指向 `http://175.178.41.19/help-cat-api/api/v1/health/ready`，判定条件是 200 且正文含 `"database":"ok"`。整机宕机时只有外部监控能发现，本机 timer 只会跟着机器一起静默。

```bash
# 服务器上装/改（配置放 /etc/help-cat/healthcheck.env，变量见 deploy/systemd/*.service 注释）
install -m 644 deploy/systemd/help-cat-healthcheck.service /etc/systemd/system/
install -m 644 deploy/systemd/help-cat-healthcheck.timer   /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now help-cat-healthcheck.timer
systemctl start help-cat-healthcheck.service && systemctl status --no-pager help-cat-healthcheck.service
```

告警 webhook 支持三种格式（`HELPCAT_ALERT_WEBHOOK_FORMAT`）：`wecom`（企业微信群机器人，默认）、`feishu`、`slack`。

日志轮转：

- nginx 与探活日志：`deploy/logrotate/help-cat` → `/etc/logrotate.d/help-cat`（每天、留 14 份、`copytruncate` 所以不需要 reload nginx）。
- 应用日志走 journald：`deploy/journald/help-cat.conf` → `/etc/systemd/journald.conf.d/help-cat.conf`（`SystemMaxUse=500M`、留 1 个月），装完 `systemctl restart systemd-journald`。
