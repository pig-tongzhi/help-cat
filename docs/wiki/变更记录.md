## 2026-09-24：把首屏做精致（77 边缘重抠 + 草地质感重做，仅本地）

状态：**未上线**，版本 `20260923-product-r19`。起因是你指出「77 跟草坪边缘糙得不行」。

### 一、边缘糙的真正原因：我上一版用硬阈值抠的像

上一版为了去掉 rembg 原始输出的灰白晕，用了"MinFilter 收 1px + 把过渡带拍成 0/255"的**硬阈值**做法 —— 结果是把晕换成了**锯齿**，而且边缘仍残留一圈米色。

现在改用 rembg 的 **alpha matting**（`alpha_matting=True` + 前景/背景阈值 + erode 12），保留约 **6.4% 的半透明像素**：边缘是绒毛过渡而不是锯齿，绿底上也没有亮边。中间试过两种"精确反解边缘色"的方案都不如它：

- `F=(C-B(1-t))/t` 精确反解：低 alpha 处把噪声放大成**斑点**；
- 给 alpha 设 0.25 下限再反解：变成**过减**，边缘出现一圈暗边。

两个失败版本的放大对比都截图看过了，最后选了"原样保留 matting 的半透明边缘"。

### 二、顺带解决的清晰度问题

源图只有 670px 宽，而首屏要显示到约 720 CSS 像素（2x 屏 = 1440 设备像素），上一版导出 760px 等于让浏览器放大 1.9 倍。现在导出 **1000px** + 轻锐化（半径 1.4 / 强度 52），并且确认了**有损 WebP 的 alpha 是无损的**（导出前后逐像素差 0），所以 95KB 就能拿到清晰边缘 —— 上一版"有损会压坏 alpha"的判断是错的。

### 三、草地重做

- 草叶从 4~9px 收细到 **2.4~5.6px**，数量按"近处 260 / 远处 140"（原来 430+300 太多，光栅化吃不住），花改成 7 瓣。
- 草线附近加了一道**柔影**（`grassShade` 渐变，最深处 26%）：草压在猫身上才有"接触阴影"，不是硬贴上去。猫身上的 `drop-shadow` 滤镜因此删掉了。
- 远景那 70 个"远处花点"删掉了：在手机上是 4~8 设备像素的浅色圆点，**看着像灰尘不像花**。
- 远处那层原来用 `feGaussianBlur` 做景深，改成"更浅的颜色 + 半透明"，零滤镜成本。

### 四、一个必须记下来的性能问题

加完这几层之后，**页面还能正常显示，但渲染帧卡住了 —— 连 headless 截图都拿不到**（`Page.captureScreenshot` 永不返回）。逐层二分：隐藏颗粒层 OK、隐藏近景草 OK、去掉远景草坪仍然 TIMEOUT —— 说明不是某一层，而是**整个首屏的合成成本超过了软件光栅化的承受范围**，去掉任意一层大图层就恢复。

代价最高的是这几样，都已删掉或降级：

1. 猫身上 1000px alpha 图的 `drop-shadow`（每帧重新做滤镜）→ 删除，接触阴影交给草地柔影；
2. 内联 SVG 的 `feGaussianBlur` 组（每次重绘重新光栅化）→ 改成浅色半透明；
3. 128px 平铺的颗粒层（一个覆盖全屏的平铺 alpha 图层）→ **整个删掉**。本来想让照片噪点与矢量草质感统一，但这个代价不划算，先放弃。

改完复测：A 当前页面 OK。这件事在手机上同样成立（弱 GPU 会更明显），所以不是"headless 的毛病"。

### 五、其它

## 2026-09-24：大图自己压缩，照片失败不再挡住建档

状态：已上线，release `20260924-image-downscale-r18`，版本 `20260923-product-r10`。

用户反馈「图片像素过大」太影响体验。原来后端默认 **5MB / 24MP**，nginx 另有一道 10MB —— 手机 48MP 照片（8000×6000）必然撞上像素上限，而且**照片传失败整个档案就建不出来**。现在四层一起改：

- **后端自己缩**：长边超过 `HELPCAT_IMAGE_MAX_SIDE`（默认 1600）就缩小后再存，不再拒绝。JPEG/MPO 先用 `Image.draft` 让解码器直接吐缩小后的位图，不必为缩放先解出整张原图（48MP 照片 0.16s / 20KB 落库）。`max_image_pixels` 从 24MP 提到 **120MP**，只当解压炸弹的硬上限；`max_image_bytes` 从 5MB 提到 **20MB**。
- **多帧不再按帧数乘像素**：MPO 以前会把帧数算进像素总数，正常照片被推过上限；现在只解码第一帧，落库也统一是单帧。
- **前端先压一道**：`api.uploadImage` 会在浏览器里把图缩到长边 1600、转 JPEG（质量 0.86）再上传，压不动（HEIC、老浏览器、canvas 出错）就退回原图交给后端。
- **照片失败不挡建档**：建档与投喂打卡都会在照片上传失败时照常提交，并提示「照片没传上去，可以发给管理员补上」；不再因为一张图丢掉整份记录。

## 2026-09-24：修手机照片被误判为「图片内容无法识别」

状态：已上线，release `20260924-mpo-upload-r17`，版本 `20260923-product-r9`。

- **根因**：白名单只认 JPEG / PNG / WEBP，而**手机相机的 HDR / 人像 / 连拍照片常常是 MPO** —— 它本质就是带多帧的 JPEG，但 Pillow 把 `format` 报成 `"MPO"`，于是被当成"不认识的格式"，返回 `image_content_mismatch`，前端显示「图片内容无法识别」。已在本地用合成 MPO 复现。
- **修法**：解码后先把 MPO 归一化成 JPEG 再查白名单、走重编码分支（否则字节会被存成 WebP 而 `content_type` 报 image/jpeg，浏览器渲染不出来 —— 第一版就踩了）。落库统一压成**单帧** JPEG，缩略图照常生成。
- **顺带放宽两类真实情况**：`image/jpg` 这类非标准 MIME 视同 `image/jpeg`；选择器**不给 MIME**（空串 / `application/octet-stream`，部分安卓与微信会这样）不再前端拦掉，改由解码结果判断。
- **报错说得清**：真不支持的格式（GIF / HEIC / AVIF…）返回新的 `unsupported_image_format`，并写明"这张实际是 X 格式"，而不是笼统的"无法识别"；前端预检也改成报出实际 MIME 并提示"iPhone 的 HEIC 可以先截图再上传"。
- 新增 `server/tests/test_media_upload_formats.py`（11 项）：MPO 收下且落成单帧 JPEG、别名与空 MIME 收下、PNG 冒充 JPEG 仍然拒、GIF 报出真实格式、明确声明的 image/heic 在入口挡掉、缩略图生成。
