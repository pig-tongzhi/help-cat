# 帮帮小猫 H5 产品体验重构设计规格

日期：2026-09-19
状态：用户确认采用方案 A，整体业务不推翻，按大厂产品风格重构 H5 首页和核心用户流程。

## 1. 背景

当前项目已经具备猫咪档案、小区候选、救助任务、管理员后台、77 故事、图片上传、微信小程序骨架等能力，但体验上仍像多轮功能堆叠后的 MVP：

- 首页视觉和功能入口不够统一，用户第一眼难以理解“帮帮小猫”到底能做什么。
- H5、后台、小程序之间的信息架构还没有完全收束，后续做微信小程序容易重复设计。
- 猫咪档案、救助任务、我的提交、管理员入口都有功能，但缺少一条清晰的普通用户主路径。
- 现有文档和测试很多，但每次视觉和功能迭代需要更明确的设计文档、实现计划、变更记录和 Git 提交流程。

本轮重构先解决用户最先接触到的 H5 体验，不推翻后端数据模型，不重写后台，不改变已有审核和权限边界。

## 2. 产品目标

第一轮目标是让 H5 看起来像一个可正式面向公众的公益产品，而不是测试页面。

核心表达：

> 让每一只小猫被认真看见，让每一次发现、照料与救助都有回音。

本轮完成后，用户打开 H5 应该能在 10 秒内理解并进入四个核心动作：

1. 了解 77 的故事和项目初心。
2. 查看猫咪档案。
3. 查看救助任务。
4. 为猫咪建档或提交线索。

管理员和超级管理员登录后仍可从“我的”进入管理后台，但首页不主动暴露运营后台信息。

## 3. 设计原则

### 3.1 大厂产品感

采用克制、清晰、可信、有温度的产品风格：

- 版式参考成熟官网和一线产品的留白、层级、节奏，而不是堆卡片。
- 视觉以真实 77 图片、黑白猫品牌符号、暖白背景和克制强调色为主。
- 页面文案少而有力，不解释系统功能，不写开发说明。
- 交互入口稳定、可预期，适合反复使用。

### 3.2 整体不变

“整体不变”在本轮解释为：

- 不更换项目定位：仍是流浪猫档案、社区、小区和救助协作平台。
- 不删除已有用户流程：登录、建档、档案、任务、我的、管理员入口继续存在。
- 不改后端核心模型：猫咪、小区候选、任务、用户、角色、审核逻辑不做结构性迁移。
- 不引入大型前端框架：继续在现有 H5 静态结构内演进，降低发布风险。

### 3.3 小程序优先

虽然本轮先重构 H5，但页面结构要为微信小程序复用：

- 首页模块和小程序首页保持同一语义顺序。
- 底部导航命名与小程序 tab 预期一致。
- 页面文案、空状态、错误状态尽量可迁移。
- 图片、卡片、任务状态的展示规则不依赖浏览器专属能力。

## 4. 本轮范围

### 4.1 包含

1. H5 首页信息架构重排
   - 顶部品牌区
   - 77 故事首屏
   - 核心行动入口
   - 猫咪档案预览
   - 救助任务预览
   - 项目可信说明

2. 核心导航体验统一
   - 首页
   - 猫咪档案
   - 救助任务
   - 我的
   - 77 的故事入口

3. 猫咪档案列表视觉重构
   - 图片比例稳定
   - 信息层级清楚
   - 状态标签克制
   - 图片失败时不破坏版式

4. 救助任务入口重构
   - 明确展示紧急程度、地点、状态和行动按钮
   - 无任务时显示可信空状态，不显示测试感文案

5. “我的”页角色识别修正体验
   - 普通用户、管理员、超级管理员有不同说明
   - 管理员入口清晰但不打扰普通用户

6. 文档和 Git 节奏
   - 每轮先写设计文档
   - 再写实现计划
   - 实现后更新变更记录
   - 每轮形成可追溯 Git 提交

### 4.2 不包含

1. 本轮不重写后端。
2. 本轮不切换数据库。
3. 本轮不接入对象存储或 CDN。
4. 本轮不完成微信小程序正式发布。
5. 本轮不新增捐赠、举报、聊天、志愿者积分等商业化/治理模块。
6. 本轮不改变管理员权限模型。

## 5. 页面结构

### 5.1 首页

首页采用“品牌叙事 + 直接行动 + 真实数据”的结构。

首屏：

- 左上品牌：圆润的 77 黑眼斑符号 + “帮帮小猫”。
- 顶部导航：77 的故事、需要帮助、猫咪档案、救助任务。
- 主标题：保留“让每一只小猫，都被认真看见”方向。
- 主 CTA：为猫咪建档。
- 次 CTA：查看救助任务。
- 视觉主体：77 真实照片或已确认的公开衍生图，背景统一，不出现分割感。

首屏下方：

- 四项成果数据或项目状态。若真实指标为空则展示 0，不写假数字。
- 猫咪档案预览：优先展示真实公开档案，最多 4 张。
- 救助任务预览：展示最新开放任务，强调地点和行动。
- 项目信任区：说明隐私保护、社区审核、公开信息脱敏。

### 5.2 猫咪档案

猫咪档案页保留现有查询和筛选能力，但视觉重构：

- 搜索与小区筛选靠近顶部。
- 卡片图片比例固定，避免加载中高度跳动。
- 每张卡片展示昵称、编号、小区/模糊位置、健康状态和公开状态。
- 图片失败显示品牌占位，不显示断裂图片图标。
- 加载更多按钮保持清晰，不自动无限滚动。

### 5.3 救助任务

救助任务页重点是让用户知道“现在能帮什么”：

- OPEN 任务优先。
- 每个任务展示标题、地点、紧急程度、任务类型、发布时间、当前状态。
- 领取任务前说明登录要求。
- 无任务时展示“暂时没有开放任务”，并提供“为猫咪建档”入口。

### 5.4 我的

“我的”页用于个人状态和角色入口：

- 未登录：展示登录/注册入口和普通用户可做的事。
- 普通用户：展示我的提交、我的任务、建档入口。
- 管理员：展示管理后台入口和审核职责。
- 超级管理员：展示超级管理员身份、后台入口、用户权限管理提示。

## 6. 数据规则

本轮前端继续使用现有 API：

- 猫咪公开列表接口
- 小区列表/候选接口
- 救助任务接口
- 登录会话接口
- 我的提交接口
- 公开指标接口

数据展示规则：

- 不写死线上假数据。
- 不因为一个接口失败阻断整个首页。
- 指标接口失败时仅该模块降级。
- 猫咪列表失败时展示可恢复错误状态。
- 图片失败时使用品牌占位图，并保留卡片尺寸。

## 7. 错误状态

错误状态必须像正式产品：

- 不在首页顶部长期显示全宽“网络连接失败”破坏首屏。
- 每个模块内部展示自己的失败、空状态或重试按钮。
- 登录失效时引导重新登录，不把用户直接卡死。
- 管理员入口 token 失效时返回 H5 登录态提示。

## 8. 响应式要求

必须覆盖：

- 360px 小屏手机
- 390px iPhone 视口
- 768px 平板
- 1024px 平板横屏
- 1440px 桌面

要求：

- 无横向滚动。
- 底部导航不遮挡主要按钮。
- 首屏 77 图片、标题和 CTA 不互相遮挡。
- 卡片图片比例稳定。
- 字体不使用随视口宽度无限缩放的写法。

## 9. 文档与 Git 规则

每轮重构都必须至少产生以下文件或更新：

1. 设计文档：`docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`
2. 实现计划：`docs/superpowers/plans/YYYY-MM-DD-<topic>.md`
3. 变更记录：`docs/wiki/变更记录.md`
4. 必要时更新：`docs/wiki/功能清单与状态.md`

提交要求：

- 设计文档单独提交。
- 实现计划单独提交或与文档修订一起提交。
- 代码实现按可验证阶段提交。
- 每次提交前运行对应测试。
- 部署前必须通过生产部署 Skill 的发布门禁。

## 10. 验收标准

第一轮重构完成后必须满足：

1. H5 首页在桌面和手机截图上接近确认设计方向，整体高级、可信、统一。
2. 用户能从首页直接进入建档、猫咪档案、救助任务、77 故事。
3. 猫咪档案和救助任务模块即使接口失败也不破坏首屏。
4. 管理员和超级管理员登录后仍能进入后台。
5. 现有核心功能不回退：登录、建档、上传图片、选择/填写小区、查看档案、查看任务、我的提交。
6. H5 合同测试、JS 测试和相关后端测试通过。
7. 本地截图覆盖 1440×900、390×844。
8. 发布后 IP 入口验证 `data-app-version` 为本轮 release。
9. 若 `https://helpcat.xyz/` 仍因备案或公网策略不可访问，必须在发布报告中明确写成域名阻塞，不把它当作代码失败。

## 11. 第一轮实施建议

第一轮建议拆成三个提交：

1. 设计与计划提交
   - 写本设计文档
   - 写实现计划

2. H5 结构与视觉提交
   - 重构 `app/rescue/index.html`
   - 重构 `app/rescue/styles.css`
   - 必要时调整 `app/rescue/app.js` 的渲染入口

3. 稳定性与发布提交
   - 完善图片失败、接口失败、版本号和测试
   - 更新 wiki 和部署文档
   - 推送 Git 并按发布 Skill 部署

## 12. 风险控制

- 不在第一轮引入新的复杂依赖。
- 不修改数据库结构，避免迁移风险。
- 不删除旧功能入口，只调整视觉和路径。
- 保留回滚能力，部署使用不可变 release。
- 如果截图和用户期望偏差大，先修视觉，不继续叠功能。
