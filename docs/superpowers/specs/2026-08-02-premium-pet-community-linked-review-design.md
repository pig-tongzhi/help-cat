# 帮帮小猫高级萌宠社区与小区联审设计

日期：2026-08-02

状态：已确认视觉方向，待用户审阅完整规格

## 1. 背景与目标

帮帮小猫已经具备 H5、管理后台、真实账号、猫咪档案、小区审核和权限治理。本轮升级同时解决三个问题：

1. 管理后台左上角品牌猫头目前只切换后台总览，无法回到 H5 主页面。
2. 普通用户创建猫咪时只能选择已审核小区，找不到小区就必须退出建档流程另行提交，体验割裂。
3. 当前视觉已经可用，但还没有形成适合大规模公众产品的高级萌宠社区品牌。

本轮目标：

- H5 与管理后台统一升级为“Apple 式留白和内容层级 + 高级萌宠社区温度”的视觉系统。
- 后台猫头成为明确、可访问的“返回帮帮小猫首页”入口。
- 普通用户可在猫咪建档内直接填写未审核的小区候选，一次提交猫咪和小区候选。
- 管理员在同一上下文中处理小区候选及其关联猫咪。
- 用户和管理员都能修正待审核或要求修改的小区候选。
- 两端页面底部展示固定品牌寄语：“安得广厦千万间，大庇天下小猫俱欢颜”。
- 设计兼顾手机、平板、桌面、无障碍、弱网和未来大规模数据量。

## 2. 非目标

本轮不实现：

- 微信小程序正式迁移。
- 地图选点和精确位置公开。
- 自动使用 AI 决定小区合并或审核结果。
- 商城、会员、支付或公开募捐。
- PostgreSQL、Redis、对象存储和多实例扩容本身。
- 完整品牌 Logo 重绘；沿用现有猫头几何标志并优化呈现。

## 3. 设计原则

### 3.1 高级而不冷漠

- 使用充足留白、强主视觉、短文案和清晰的视觉层级。
- 可爱元素只用于猫头、爪印、状态和空页面插图，避免幼儿化。
- 用户端温暖亲和；后台更克制、专业、数据化。

### 3.2 真实内容优先

- 猫咪照片和救助状态是主角，装饰不能压过内容。
- 无照片时使用稳定的品牌占位，不制造大面积空白。
- 审核状态、隐私和行动按钮必须比装饰更清楚。

### 3.3 一次提交、不中断流程

- 用户在建档内选择已有小区或填写新小区候选。
- 客户端只提交一次，后端事务保证小区候选和猫咪同时成功或同时失败。
- 不把用户带离当前建档弹层，也不丢失已经填写的猫咪信息。

### 3.4 审核优先修正，不轻易丢弃

- 小区候选优先通过、合并或要求修改。
- 彻底驳回只用于广告、恶意、虚假或完全无效信息。
- 小区候选失效时，关联猫咪保留原始线索并保持待审核，不转换为语义模糊的“未归属小区”。

## 4. 视觉系统

### 4.1 色彩

- 画布：暖白 `#F5F5F7`，主要表面 `#FFFFFF`。
- 主要文字：深墨黑 `#1D1D1F`，次要文字 `#6E6E73`。
- 品牌主色：柔和杏橙，用于主要行动和猫咪温度。
- 辅助色：雾紫、薄荷绿、浅金，仅用于分类和状态。
- 危险与驳回使用克制红色，不以颜色作为唯一信息载体。

最终实现应继续通过 CSS 变量维护语义色，不在组件中散落色值。

### 4.2 字体与排版

- 使用系统字体栈，优先匹配 Apple 平台和主流中文系统字体。
- 首页主标题使用响应式 `clamp()`，手机不过度占屏，桌面形成强主视觉。
- 正文控制行宽和行高，避免大屏出现超长行。
- 数字、状态和操作标签使用稳定层级，避免过多全大写英文。

### 4.3 表面与动效

- 减少重边框和多层阴影，主要依靠留白、背景层次和圆角分组。
- 图片卡片使用一致比例、响应式图片和失败占位。
- 动效持续时间控制在 160–320 ms，用于进入、切换和状态变化。
- 完整支持 `prefers-reduced-motion: reduce`。
- 不使用会阻塞交互的大型滚动特效、背景视频或高成本粒子动画。

### 4.4 无障碍

- 所有交互目标最小 44×44 CSS 像素。
- 猫头返回入口具有可见文案或辅助名称“返回帮帮小猫首页”。
- 键盘可到达、焦点清晰，状态变化使用 `aria-live`。
- 正文与背景、按钮与背景满足可读对比度。
- 页脚寄语使用真实文本，不烘焙进图片。

## 5. H5 用户端设计

### 5.1 首页

- 顶部品牌栏保持轻量，滚动后可使用半透明表面，但不能降低文字对比度。
- 首屏采用高质量猫咪主视觉、核心愿景短句和一个主要行动“帮助一只小猫”。
- 数据指标改为轻量信息带，展示公开猫咪、开放任务和已覆盖小区。
- 猫咪卡片优先展示图片、名称、小区、健康与审核状态。
- 首页信息量按移动端优先排序，桌面可扩展为更宽网格。

### 5.2 猫咪建档第二步

“小区和位置”步骤改为两个模式：

1. **选择已有小区**：搜索并选择 ACTIVE 小区。
2. **填写新小区**：输入小区名称、街道和可选补充说明。

默认显示“选择已有小区”。用户搜索无结果时，在当前步骤内出现“没有找到？填写新小区”，切换后保留猫咪其他字段。

填写新小区时：

- 输入名称后展示可能重复的 ACTIVE 或 PENDING_REVIEW 候选。
- 用户可以改选已有小区，或确认“仍然提交新小区候选”。
- 提交前明确提示：“小区与猫咪都会进入审核；小区确认后才能公开猫咪档案。”
- 不要求用户先离开建档页单独创建小区。

### 5.3 我的提交

- 猫咪提交项显示关联小区的状态：待审核、要求修改、已合并、已通过或已驳回。
- 小区为 `NEEDS_CHANGES` 时，原提交用户可以修改名称、街道和说明。
- 修改后回到 `PENDING_REVIEW`，猫咪保持待审核。
- 若候选被合并，提交记录显示“已合并至：正式小区名称”。

### 5.4 页脚寄语

H5 主内容末尾增加语义化页脚：

> 安得广厦千万间，大庇天下小猫俱欢颜

- 手机端位于底部导航安全区上方，不被固定导航遮挡。
- 桌面端位于页面内容末尾，使用小号、低强调但保持可读的文字。

## 6. 管理后台设计

### 6.1 品牌猫头返回主页面

- 左上角 `.side-brand` 不再指向 `#overview`。
- 使用真实链接 `/help-cat/rescue/index.html#home`。
- 辅助名称和悬停提示为“返回帮帮小猫首页”。
- 同源页面保留 H5 Session，不复制、暴露或拼接 Token 到 URL。
- 后台总览仍由独立“总览”导航按钮负责。

### 6.2 小区与猫咪联审工作台

待审核小区使用联审卡片，展示：

- 候选小区名称、街道、提交人、提交时间和修改历史。
- 相似的正式小区和其他待审核候选。
- 所有关联猫咪的缩略卡片、名称、模糊位置和提交状态。

管理员操作：

1. **通过**：候选变为 ACTIVE，关联猫咪解除小区阻塞，继续猫咪审核。
2. **合并**：选择一个 ACTIVE 目标小区，事务内把关联猫咪改挂目标小区，候选变为 MERGED。
3. **要求修改**：填写原因，候选变为 NEEDS_CHANGES，通知原提交用户；管理员也可直接修正后重新提交审核。
4. **驳回**：必须填写原因，仅用于恶意或无效内容；候选变为 REJECTED，关联猫咪保持 PENDING_REVIEW 并标记“小区信息待修正”。

管理员不能在候选仍为 PENDING_REVIEW、NEEDS_CHANGES 或 REJECTED 时公开关联猫咪。可以先把猫咪改挂到已有 ACTIVE 小区，再完成猫咪审核。

### 6.3 后台页脚

后台主内容末尾展示同一句寄语：

> 安得广厦千万间，大庇天下小猫俱欢颜

侧栏较长时寄语不应与“服务运行中”混在一起；它属于页面内容页脚，而不是运行状态。

## 7. 数据模型

### 7.1 communities 扩展

在现有小区实体上增加：

- `normalized_name`：用于精确规范化查重。
- `status` 新增 `NEEDS_CHANGES`、`MERGED`。
- `review_note`：要求修改或驳回原因。
- `merged_into_id`：MERGED 时指向 ACTIVE 小区。
- `updated_at`：修正时间。

原有 `PENDING_REVIEW`、`ACTIVE`、`REJECTED`、`ARCHIVED` 保留。

### 7.2 cats 关联

- 猫咪继续使用非空 `community_id`，候选小区本身也是 communities 记录，因此无需制造空归属。
- 猫咪是否可公开由自身审核状态和关联小区状态共同决定。
- 后端返回派生字段 `community_review_blocker`，前端不自行猜测阻塞原因。

### 7.3 审计

以下行为写入审计日志：

- 创建候选小区与关联猫咪。
- 用户或管理员修改候选。
- 通过、合并、要求修改、驳回。
- 关联猫咪批量改挂正式小区。
- 管理员手动修正候选字段。

## 8. API 与事务

### 8.1 一次提交

`POST /api/v1/cats` 接受二选一：

- `community_id`
- `community_candidate: { name, street, note? }`

后端流程：

1. 校验只有一个来源。
2. 规范化名称并查找相同 ACTIVE/PENDING_REVIEW 候选。
3. 若用户明确选择现有结果，复用其 ID；否则创建 PENDING_REVIEW 候选。
4. 创建 PENDING_REVIEW 猫咪并关联小区。
5. 在同一数据库事务中提交。

任何一步失败都不留下孤立小区或孤立猫咪。

### 8.2 候选修改

- `PATCH /api/v1/communities/{id}`
- 原提交用户只能修改自己创建且处于 PENDING_REVIEW/NEEDS_CHANGES 的候选。
- ADMIN/SUPER_ADMIN 可修改非归档候选。
- 使用版本号或 `updated_at` 做乐观并发控制，冲突返回 409。

### 8.3 联审操作

- `POST /api/v1/communities/{id}/review`：approve、request_changes、reject。
- `POST /api/v1/communities/{id}/merge`：目标必须为 ACTIVE 且不能是自身。
- 合并、批量改挂猫咪、候选状态更新和审计写入必须处于同一事务。
- 重复请求使用幂等键或状态前置条件避免二次合并。

## 9. 查重策略

- 首版只做确定性的名称规范化和模糊候选提示，不自动合并。
- 规范化包括去除首尾空格、统一大小写/全半角、压缩连续空白和常见标点。
- 相似结果仅帮助用户和管理员判断，最终合并必须人工确认。
- 数据库约束防止同一辖区内产生两个完全相同的 ACTIVE 规范化名称。

## 10. 错误与边界处理

- 候选创建成功但猫咪创建失败：事务整体回滚。
- 两名管理员同时审核：后提交者收到 409 和最新状态，不覆盖前者结果。
- 合并目标在操作期间被归档：事务失败并提示重新选择。
- 用户修改时管理员已审核：返回 409，客户端刷新为最新状态。
- 弱网重复点击：提交按钮锁定，并使用幂等键阻止重复记录。
- 图片上传失败：保留表单和候选小区字段，允许重试或无图提交。
- 用户输入恶意 HTML：后端保存纯文本限制长度，前端输出继续转义。

## 11. 面向大规模使用的前端约束

“几十万用户”不等于一次性在浏览器加载几十万条数据。本轮界面必须为后续扩容保留正确边界：

- 所有列表使用分页或游标，不依赖一次性完整返回。
- 搜索使用防抖和取消过期请求。
- 图片使用响应式尺寸、懒加载、占位和失败回退。
- 不在首屏加载审核历史、全部任务或全部小区。
- 管理后台联审列表按状态和时间分页，关联猫咪采用限量预览和“查看全部”。
- 动效不阻塞输入、滚动和低端手机主线程。
- CSS 继续移动优先，覆盖 360、390、430、768、820、1024 和 1280+ 宽度。

数据库和部署层面的 PostgreSQL、对象存储、Redis、多实例与监控仍按现有规模化路线图单独实施，不能仅靠本轮 UI 宣称已经支持几十万并发。

## 12. 测试与验收

### 12.1 自动化

- 后台猫头链接目标、辅助名称和 Token 不进入 URL。
- USER 使用 ACTIVE 小区创建猫咪。
- USER 一次提交新候选小区和猫咪，验证原子性。
- 相同规范名的重复候选提示和并发约束。
- 用户只能修改自己的待审/待修改候选。
- ADMIN/SUPER_ADMIN 通过、合并、要求修改和驳回。
- 合并后所有关联猫咪改挂目标小区。
- 非 ACTIVE 小区阻止猫咪公开。
- 冲突、重复点击、弱网失败和事务回滚。
- H5 与后台均存在页脚寄语。
- 响应式、键盘焦点、减少动效和图片失败状态。

### 12.2 线上验收

- 已登录超级管理员从 H5 进入后台，再点击猫头返回 H5 首页，身份保持正确。
- 普通用户在建档内填写新小区，一次提交后在“我的提交”看到两者状态。
- 管理员在联审卡片中通过或合并小区，然后继续审核猫咪。
- 要求修改后，用户可修正并重新进入待审。
- 手机、平板、桌面无横向溢出，底部导航不遮挡寄语。
- 本地、release 与生产静态文件哈希一致，部署可回滚。

## 13. 发布策略

1. 数据库迁移前完成备份并验证回滚。
2. 后端先发布兼容旧客户端的字段与接口。
3. 管理后台发布联审能力。
4. H5 发布内联候选小区流程和新视觉。
5. 使用受控 QA 数据覆盖所有新增状态。
6. 生产小流量验收后再扩大真实用户范围。

本轮继续在现有功能分支和 Draft PR 中迭代，不自动合并 `main`。
