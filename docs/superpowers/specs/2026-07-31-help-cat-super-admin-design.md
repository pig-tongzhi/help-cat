# 帮帮小猫唯一超级管理员与用户赋权设计

## 目标

在现有 `USER`、`ADMIN` 权限模型上增加唯一的 `SUPER_ADMIN`。线上现有账号 `zack` 是唯一超级管理员，可以在管理后台将普通用户提升为管理员，也可以撤销管理员权限。普通管理员继续负责猫咪、小区和任务治理，但不能修改用户角色。

## 权限模型

| 角色 | 公开浏览 | 提交档案/领取任务 | 内容审核 | 用户赋权 |
| --- | --- | --- | --- | --- |
| `USER` | 是 | 是 | 否 | 否 |
| `ADMIN` | 是 | 是 | 是 | 否 |
| `SUPER_ADMIN` | 是 | 是 | 是 | 是 |

系统不提供创建第二个超级管理员的接口。`zack` 的 `SUPER_ADMIN` 角色通过一次性生产迁移设置；后台角色接口只接受 `USER` 或 `ADMIN`，并拒绝修改任何 `SUPER_ADMIN` 账号。

## 后端接口

- `GET /api/v1/admin/users`：仅 `SUPER_ADMIN` 可访问，返回用户编号、用户名、昵称、角色、状态和创建时间；不返回密码哈希、openid、会话或令牌。
- `POST /api/v1/admin/users/{user_id}/role`：仅 `SUPER_ADMIN` 可访问，请求体为 `{ "role": "USER" | "ADMIN" }`。
- 角色修改写入现有 `audit_logs`，动作名为 `ROLE_CHANGE`，保存修改前后角色。
- 现有内容治理接口把 `ADMIN` 和 `SUPER_ADMIN` 都视为管理员。
- 注册用户始终默认为 `USER`；不再允许通过用户名环境变量自动创建管理员，避免绕过唯一超级管理员治理。

## 管理后台

后台新增“用户与权限”面板：

- 登录成功后先读取 `/auth/me` 确认角色。
- `USER` 拒绝进入后台。
- `ADMIN` 可以使用现有猫咪和小区治理界面，但看不到用户权限面板。
- `SUPER_ADMIN` 可以搜索用户、查看角色，并执行“设为管理员”或“撤销管理员”。
- 超级管理员自身显示“唯一超级管理员”，不出现角色修改按钮。
- 角色修改期间按钮禁用，成功后刷新用户列表；接口错误以页面提示显示，不使用阻塞式弹窗。

## 数据与迁移

无需新增数据库列。部署时在事务中把 `username = 'zack'` 的唯一活动账号更新为 `SUPER_ADMIN`，并断言：

1. `zack` 恰好存在一个；
2. 更新后 `SUPER_ADMIN` 恰好一个；
3. 其他账号不能是 `SUPER_ADMIN`。

失败则回滚部署，不启动新版本。

## 安全与错误处理

- 无令牌返回 `401 unauthorized`。
- 普通用户或管理员调用用户管理接口返回 `403 super_admin_required`。
- 修改不存在用户返回 `404 user_not_found`。
- 角色不是 `USER`/`ADMIN` 返回请求校验错误。
- 修改超级管理员返回 `409 super_admin_immutable`。
- 重复设置相同角色保持幂等，但仍返回当前用户数据，不产生多余审计记录。

## 验证

- API 测试覆盖角色矩阵、唯一超级管理员不可变、升降级、审计日志和敏感字段不泄露。
- 前端契约测试覆盖用户管理面板、接口路径、角色判断和错误状态。
- 全量单元测试必须通过。
- 浏览器回归覆盖超级管理员登录、用户列表、提升管理员、撤销管理员，以及普通管理员看不到用户管理面板。
- 上线前备份数据库、后端和管理端静态文件；上线后验证服务、Nginx、公开站和管理后台。
